## Finding from live testing (spec gap, PM's)

The PM's live drain of the 148 production rows was rejected after 10 requests:
`Rate limit exceeded. Consumed (req/min): 11, Remaining (req/min): 0` (HTTP 429,
`retry-after: 58`). Measured: **the plan allows 10 scrape requests per minute.**
The spec only accounted for concurrency (2). With the delivered code:

- a 429 is handled as a per-site failure, so `enrichBusinessLinks` stamps
  `enrichedAt` and the row is shelved for 7 days. A 50-row seed or a 40-row
  cron drain would shelve most of its rows on the first run;
- `syncStale` records a 429 with `markScrapeFailed`, putting healthy rows into
  scrape back-off;
- nothing paces requests: website scrapes run with no gap, and the Trustpilot
  limiter's 1.5 s gap still allows 40 a minute.

## Verdict
REVISE (round 1). The package met every criterion as written; the criteria
missed the rate limit. Spec and architecture are amended (R8, R9, AC13–AC18).

## Required changes

1. **Pace every Firecrawl request (AC-17.13).** One process-wide limiter in
   `client.ts`, shared by `scrapeJson` and `scrapePage`: no more than
   `FIRECRAWL_REQUESTS_PER_MINUTE` request starts in any rolling 60 s (new
   optional env var read through `src/lib/env.ts`, default 10, minimum 1).
   It applies on top of the existing concurrency rules (Trustpilot 1 in
   flight / 1.5 s apart, websites 2 in flight). Observed: 142 requests in 8 s.
   Expected: the 11th request of a minute waits for the window. Proof: a unit
   test of the limiter with an injected clock/timer.
2. **Map HTTP 429 from the Firecrawl API to a typed error (AC-17.14).**
   `export class FirecrawlRateLimited extends Error { retryAfterMs: number }`
   in `client.ts`, thrown by both seam methods when the API answers 429;
   `retryAfterMs` from `Retry-After` when the SDK exposes it, else 60 000.
   Check live how SDK v4 surfaces a 429 (you may spend up to 12 more live
   requests to trigger one). Proof: unit test of the mapping function with an
   SDK-shaped error, plus the live observation in the report.
3. **A rate limit is not a site failure (AC-17.15).** `resolveExternalLinks`
   and `enrichBusinessLinks` propagate `FirecrawlRateLimited` (as they do
   `DiscoveryUnavailable`) and write nothing: `enrichedAt` stays null. A 429
   on the contact page keeps the homepage result and does not throw. Proof:
   tests.
4. **The drain waits or stops (AC-17.16).** In `enrichPendingLinks`, on
   `FirecrawlRateLimited`: if `retryAfterMs` plus 10 s still fits the remaining
   budget, wait (`opts.sleep?: (ms: number) => Promise<void>`, injectable) and
   retry that row; otherwise stop starting rows. Rate-limited rows are not
   counted as failed and stay pending. The result gains `rateLimited: boolean`
   (additive). Proof: tests with injected clock and sleep.
5. **`syncStale` stops on a rate limit (AC-17.17)** without `markScrapeFailed`
   for that row, and returns what it did so far. `scrapeUrlAction`: a rate
   limit in the profile scrape returns `fail` with a message containing
   "rate limit"; a rate limit in the link step still returns `ok` and leaves
   the row unstamped. Proof: tests.
6. **Cron links budget (AC-17.18).** `links` budget = the remaining discovery
   budget capped at 180 s on non-Sundays, 60 s on Sundays (the seed needs the
   rest); limit stays 40; the stage reports `rateLimited`. Proof: test.
7. **AC-17.9 again:** typecheck, lint (0 warnings) and the full suite green.
